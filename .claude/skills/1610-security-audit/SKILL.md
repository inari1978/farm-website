# 1610-security-audit（ソースコード・セキュリティ監査）

## 目的
コードベースから**実在する信頼境界の破れ**を見つけ、オーナーにソース上の根拠・優先度・最小の修正案を渡す。防御目的・ソース起点の監査である。影響を受ける主体・リソース・具体的な結果を示せない候補は、脆弱性として確定しない。

本スキルは Cloudflare の [security-audit-skill](https://github.com/cloudflare/security-audit-skill)（MIT License）の方法論を踏襲し、本フレームワーク（Windows／個人運用／日本語ドキュメント）向けに簡略化したものである。原文は `references/` に同梱している。

## 動作モード
本スキルの読み込みは、フル監査の実行やファイル作成を許可するものではない。

| モード | 発動条件 | 動き |
|---|---|---|
| **ガイダンスモード**（既定） | 特定箇所のレビュー、セキュリティの質問、個別指摘の調査 | 必要な節だけ使う。全フェーズ実行・成果物ファイル作成はしない |
| **フル監査モード** | 「コードベースを監査して」「全体の脆弱性診断」「監査報告書を作って」など明示的な依頼 | 全フェーズを実行し、報告書を出力する |

どちらか曖昧な場合は、ファイル作成や全工程の開始前に1問だけ確認する。

## 実行安全ルール（両モード共通）
- **対象コードは実行しない（ソースのみの監査）。** 元スキルは OS 強制サンドボックス（外部通信遮断・空の環境変数・読み取り専用・リソース制限）内での実行を前提とするが、本環境（Windowsネイティブ）ではそれを強制できないため、ビルド・テスト・対象プロセスの起動は行わない
- 実行しないと判断できない事実は `要確認`（needs_validation）とし、「安全な確認手順」を書く。推測で confirmed にしない
- デプロイ済み環境・外部サービス・本番ID・他者のデータ・共有インフラには一切アクセスしない
- 依存パッケージのインストールや取得をしない
- 秘密情報を見つけても値を報告書に転記しない（ファイルパスと行番号、種別のみ記載）

> ユーザーが WSL2／コンテナ等で上記サンドボックス条件を満たす環境を用意した場合に限り、`references/` の原文の手順に沿って局所的な再現確認を行ってよい。その場合も事前にユーザーの承認を得る。

## 入力
- 対象リポジトリのルートパス（既定: カレントディレクトリ）
- 任意指定:
  - **プロファイル**: `quick`／`standard`（既定）／`deep`
  - **スコープ**: 特定パス、特定サブシステム、2つのコミット間の差分
  - **前回の監査報告書**（あれば差分監査に使う）

## 出力
| 成果物 | 形式 | ファイル名 |
|---|---|---|
| セキュリティ監査報告書 | Markdown | `セキュリティ監査報告書_[PJ名]_v[版].md` |

- 既定の出力先: `docs/04_テスト/セキュリティ監査/`（存在しなければ作成）
- 報告書には脆弱性の所在が含まれる。**出力前に、出力先がGit管理下で公開リポジトリにpushされ得るかを確認し、該当する場合はユーザーに出力先を確認する**
- 雛形: `templates/security-audit-report-template.md`

## プロファイル
| プロファイル | 用途 | 探索 | 検証 |
|---|---|---|---|
| `quick` | 小規模・初回の当たり付け | 攻撃クラスを統合し3〜4 Agent | 候補ごとに1回の独立反証（Phase 3と4を兼ねる） |
| `standard` | 通常 | 攻撃クラスごとに1 Agent | Phase 3 で全候補を反証、Phase 4 で critical/high を再確認 |
| `deep` | 高リスク・大規模 | サブシステム×攻撃クラスで分割 | Phase 3・4 を全 confirmed で別Agentにより実施 |

プロファイルが変えるのは網羅の広さだけで、**判定の基準は変えない**。`quick` やスコープ限定の監査は、報告書冒頭で「部分的な監査」と明記する。

## フル監査ワークフロー

### Phase 0: セットアップ
1. 対象ルート、リポジトリ名、監査対象コミット（`git rev-parse HEAD`）と作業ツリーの汚れ（`git status --porcelain`）を記録する
2. 前回の監査報告書があれば読み、前回の confirmed／要確認を今回の検証対象に含める（ソースが変わっていれば再検証扱い。前回の結果だけを根拠に「問題なし」としない）
3. プロファイルとスコープを決め、ユーザーに1行で示す

### Phase 1: 偵察（並列Agent・読み取り専用）
`Agent`（`general-purpose`）を1メッセージで並列起動する。各Agentはファイルを書かず、`file:line` 付きの事実だけを返す。

| Agent | 調べること |
|---|---|
| 1a 製品とスタック | 製品の種類、利用者・運用者、言語・FW・ビルド、エントリポイントとサブシステム境界、比較可能な類似ソフト |
| 1b 主体・権限・統制 | 低信頼の主体と設計上許された操作、各入口の認証、リソース単位の認可・テナント境界、特権の変化・取消・フォールバック、**ソースで見える統制と、デプロイ設定に依存する統制の区別** |
| 1c 入力面とシンク | 外部入力が入る全箇所（HTTP、RPC/メッセージ、ファイル/アーカイブ、CLI/環境変数/設定、プラグイン/CI、モデル入力/ツール引数、IPC 等）、主要な変換、保存・派生コピー、危険なシンク |

親（メイン会話）が結果を統合し、報告書の付録用に以下をまとめる:
- **アーキテクチャ要約**（約1,000字以内）: 主体・保護対象・信頼境界と最も強い統制・入力面・主要な source→sink 経路
- **観点×対象表**（網羅の台帳）: 行＝入力面×信頼境界、列＝適用する攻撃クラス。各セルに 未着手／確認済／候補あり／要確認／対象外（理由）を記録する
- **適用する攻撃クラスの選定**: `attack-classes.md` から選ぶ。ドメイン別資料（`references/*.md`）は、その「When to use this file」に該当する境界が偵察で**実際に見つかった場合だけ**選ぶ（言語名・依存名が出てくるだけでは選ばない）

### Phase 2: 攻撃クラス別の探索（並列Agent）
攻撃クラス（または関連する観点のまとまり）ごとに `Agent`（`general-purpose`）を並列起動する。1 Agent に無関係な境界を混ぜない。

**探索Agentへのプロンプトに必ず含めるもの**（この順序で）:
1. 役割: 「担当範囲で、ソースに根拠のあるセキュリティ不変条件の破れを見つけ、末尾の形式の JSON を1つだけ返す」
2. アーキテクチャ要約（全文）
3. 担当する観点×対象のセルと開始パス
4. 担当攻撃クラスの記述（`attack-classes.md` の該当節、選定したドメイン別資料の `Core discipline`／該当節／`Universal moves`／`Validation rules` を**原文のまま**貼る。名前だけ渡さない）
5. 下記「探索の方法」と「候補ゲート」
6. 他Agentの担当範囲（重複させない）

**探索の方法**（プロンプトに含める）:
```text
ソースレビューのみ行う。対象コードの実行・外部通信・依存の取得はしない。

コードを深く読む。担当の入力を、パース→本人確認→認可→正規化→状態→派生コピー→最終シンクまで追う。
同じ結果を生む兄弟・レガシー・バッチ・リトライ・キャンセル・移行・エラー経路も読む。
統制の「有無」ではなく「同等性」を比べ、あるコンポーネントの保証と次のコンポーネントの前提を比べる。

具体的な不変条件から考える:
1. 低信頼の主体と、その初期能力を名指す
2. 受け入れられる値・操作・状態遷移・リソース指定子を名指す
3. それを拒否・束縛・隔離・制限・取消すべき統制の場所を特定する
4. その判断の後のソース経路を正確に追う
5. 最小の影響（ダミーレコード1件、誤った戻り値など）で止める
6. 不変条件を強制するソース修正と回帰テストを示す

異常系を試す: 欠落・空・0・負・最大・超過・重複・混在エンコード・失効・取消済・順序入替・並行・移行途中・依存失敗・ロールバック。
パーサや方針の受け渡し箇所ごとに正規化と単位を比べる。

デプロイ・ブラウザ・プロバイダ・プロキシ・OS・パッケージ・秘密・IDの事実がソース外にある場合、
それはどちらの証拠にもならない。決定的なら needs_validation にし、欠けている観測事実と安全な確認手順を書く。
不変条件の成否が決まった時点でその線の調査をやめ、結果を記録する。
```

**候補ゲート**（プロンプトに含める）:
```text
1. 候補には、主張する根本原因の完全なソース経路（リポジトリ相対パス:行）と、経路上で最も強い統制の記述が必要。
2. confirmed の提案には、境界をまたぐ意味のある影響、完全な成立条件、それを防ぐ層がソース上に見えないことが必要。
3. クラッシュをコード実行に、通常処理を共有資源の枯渇に、同一主体の操作を権限昇格に格上げしない。
4. ソースから判断できない事実が必要なら needs_validation。深刻度を付けない。
5. 影響を受ける主体・リソースのないベストプラクティス不足は、指摘ではなく hardening（強化提案）に回す。
   ソースで否定される候補は needs_validation にしない。
6. 同じ根本原因には同じ fingerprint（例: authz:missing-owner-check:api/users）を使う。行番号・深刻度・判定を含めない。
7. ゲートを通るものがなければ候補は空配列で返す。
```

**探索Agentの返却形式**（JSONのみ。前後に文章を付けない）:
```json
{
  "cells": [{"cell": "担当セル", "disposition": "covered|candidate|blocked", "reviewed_paths": ["..."], "invariant": "確認した統制", "result": "ソースで確認できたこと", "unresolved": []}],
  "candidates": [{
    "fingerprint": "...", "proposed_verdict": "confirmed|needs_validation",
    "title": "...", "description": "...",
    "principal": "低信頼の主体", "boundary": "破られる境界", "affected": "影響を受ける主体・リソース",
    "trace": [{"role": "entrypoint|propagation|sink", "path": "repo/relative:行", "note": "..."}],
    "strongest_control": "経路上で最も強い統制とその場所",
    "conditions": ["成立条件"], "impact": "具体的な結果",
    "severity": {"likelihood": "...", "impact": "...", "overall": "critical|high|medium|low|informational"},
    "remediation": "最小のソース修正と回帰テスト",
    "blockers": ["needs_validationの場合: 欠けている事実"], "validation_plan": "needs_validationの場合: 安全な確認手順"
  }],
  "hardening": ["指摘ではない強化提案"],
  "uncovered": [{"surface": "...", "boundary": "...", "reason": "担当外で別途確認が必要な理由"}]
}
```

親は返却を統合する: 形式不正の結果は修復せず、そのセルを未着手に戻して再割当てする。fingerprint と根本原因で重複をまとめる。`uncovered` は観点×対象表に新しい行として追加し、次の探索で割り当てる（`quick` では「未実施」として記録のみ）。

**網羅チェック**（`standard`／`deep`）: 探索後に別の `Agent` を1つ起動し、観点×対象表とアーキテクチャ要約を渡して「未マップの入口、未確認の並行経路、根拠のない対象外判定、経路を見ずに確認済とされたセル」を探させる。指摘があれば追加探索を1回行う。

### Phase 3: 独立反証（候補ごとに新規Agent）
すべての候補（confirmed 提案・needs_validation 提案の両方）を、**その候補を探索していない新規の `Agent`** に1件ずつ渡す。検証Agentには読み取り専用の `security-reviewer`（反証モード）を使う。並列起動してよい。他の検証Agentの結論は渡さない。

**検証Agentのプロンプト**:
```text
あなたはこの候補を書いていない。リポジトリのソースから、この候補の反証を試みよ。
対象コードの実行・外部通信はしない。

1. trace と根拠の全ファイル・行番号・説明を自分で読み直して確認する。
   先頭が本当に低信頼の入口で、末尾が主張するシンク・境界の影響であることを確認する。
2. 経路上の検証・本人確認・認可・正規化・ライフサイクル・FW・隔離の統制のうち、
   ソースで見える最も強いものを再構成する。
3. confirmed 提案なら、入力・インタフェース・成立条件・影響を受ける主体を独立に確かめる。
   証拠以上に強い結果を推論しない。
4. 可能性・影響・深刻度・修正案が、証拠で示せる範囲に収まっているか確認する。
5. needs_validation 提案なら、欠けている事実が本当にソース外かを判断する。
   ソースで否定できるなら rejected。決定的な事実が残るなら needs_validation のまま、確認手順を正確にする。
6. 同じ根本原因なら fingerprint を変えない。

JSONを1つだけ返す（前後に文章を付けない）:
{"decision": "confirmed|needs_validation|rejected", "record": {候補と同じ形式。rejectedなら "reason" を含める}}
修正した record は探索者の記述を置き換える。
```

判定の扱い:
- needs_validation → confirmed への格上げは、検証Agentが経路と影響を独立に確立した場合のみ
- 特定のデプロイ・実行時の事実が不明なら confirmed → needs_validation に格下げ
- ソース・見える統制・意味のある影響の欠如・成立し得ない前提で否定されたら rejected
- **needs_validation は思いつきの置き場ではない**

### Phase 4: 最終確認（新規Agent）
`standard` では critical／high の confirmed、`deep` では全 confirmed と全 needs_validation を、Phase 2・3 に関与していない新規の `security-reviewer` Agent に渡し、記録（パス・行・入力・条件・影響・深刻度・修正案）を再確認させる。返却は `{"decision":"verified"}` または `{"decision":"replace","reason":"...","record":{...}}`。

判定の格上げ、根本原因・影響・深刻度の実質的な変更を伴う replace は、そのまま適用せず、さらに別の新規Agentで確認してから適用する。文言や行番号だけの修正は直接適用してよい。

### Phase 5: 報告書の作成
Phase 4 を通過した記録だけから、`templates/security-audit-report-template.md` に従って報告書を書く。報告書の文章で判定・深刻度・影響を変えない。rejected は指摘として扱わない（前回との食い違いの説明に必要な場合だけ fingerprint を記載）。

confirmed が0件でもそのまま報告する。**指摘を水増しするために low を作らない。**

## 判定の定義
| 判定 | 意味 | 深刻度 |
|---|---|---|
| **confirmed** | ソース経路が完全に追跡でき、境界をまたぐ具体的な影響が示せる | 付ける |
| **要確認**（needs_validation） | ソースに根拠のある境界仮説だが、ソース外の特定の事実が決定的に欠けている。欠けている事実と安全な確認手順を明記する | **付けない** |
| **rejected** | 検証で否定された。次回同じ主張を繰り返さないため、監査作業記録には残す | 付けない |

## 深刻度の基準（confirmed のみ）
| 深刻度 | 目安 |
|---|---|
| **critical** | 未認証の攻撃者がコード実行、データストア全体へのアクセス、任意アカウントの乗っ取りを得る |
| **high** | 明示的なセキュリティ統制を完全に破り、実害がある（認証回避、テナント越境の読み書き、他ユーザーに影響する格納型スクリプト実行、認証後のコード実行、共有サービスの未認証リモート停止） |
| **medium** | 実在する境界の破れだが、影響範囲が限定的・前提条件が珍しい・狭いリソースに限られる |
| **low** | 秘密ではない内部情報の露出、または継続的な労力に対して得るものが小さい |
| **informational** | 確定しているが影響は最小。主に大きな指摘の前提条件として有用 |

high と medium の判別: **実害のある操作について、明示的な統制を「完全に破る」のか「弱めるだけ」か。** 具体的な被害を言えないなら、深刻度は感覚より低い。総合深刻度は、示した影響を超えない。

## 修正案の書き方
confirmed ごとに、コードが守るべき**不変条件**と、それを**最後の信頼できる判断箇所**で強制する最も狭いソース変更を示す。一般的な強化アドバイスより、リポジトリ相対パスでの具体的変更と回帰テストを優先する。監査は修正を記述するだけで、対象ソースは変更しない（修正はユーザーの指示があってから別タスクで行う）。

## アンチパターン
1. チェックリストからの逸脱を脆弱性として出す
2. 到達可能な境界の破れがない多層防御アドバイスを指摘にする
3. ソースにないプロバイダ・プロキシ・ブラウザ・ID・デプロイの挙動を推測する
4. 設計上同一主体に許された権限や、自分自身への影響を境界越えとして扱う
5. パーサや実行時の影響を、観測できた以上に強く書く
6. 重複排除も検証もできない文章だけの探索結果を受け入れる
7. 前回の confirmed を、ソースが変わっていないことを確かめずに再掲する／探索の手本として渡して探索を偏らせる
8. 要確認に深刻度を付ける
9. 独立検証の前に報告書を書く、または報告書と記録が食い違う

## よくある落とし穴
| 落とし穴 | 対処 |
|---|---|
| 探索したAgentに自分の指摘を検証させてしまう | 検証は必ず新規Agent。探索Agentに追加質問して検証の代わりにしない |
| 「ソースから分からない」ものを推測で confirmed にする | 要確認にして、オーナーが見るべき設定・ID・経路を具体的に書く |
| ドメイン別資料を名前だけ渡し、探索Agentが中身を知らない | 該当節を原文のまま貼る |
| 報告書に見つけた秘密情報の値を書く | パス・行・種別だけ書き、値は伏せる |
| 監査報告書を公開リポジトリにコミットしてしまう | 出力前に出力先を確認する。必要なら `.gitignore` 対象のディレクトリにする |
| 1回の監査で「全部見た」と言ってしまう | 観点×対象表の未着手・対象外・要確認を報告書に必ず載せる |

## 関連ペルソナ・Agent
- 判断基準: `.claude/personas/security/CLAUDE.md`（親は監査開始時に読み込む）
- 検証・最終確認: `security-reviewer` Agent（読み取り専用、反証モード）
- 偵察・探索: `general-purpose` Agent（深い追跡が必要なため）

## 関連スキルとの使い分け
- 差分（PR・コミット前）だけのセキュリティレビュー → 標準の `/security-review`
- セキュリティ**設計書**の作成 → `1311-basic-design-security`
- 設計書・ドキュメントのレビュー → `1500-document-review`
- セキュリティテストの設計 → `1600-detailed-design-test`（本スキルの要確認一覧を入力にできる）
